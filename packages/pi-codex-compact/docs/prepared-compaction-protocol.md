# Prepared-compaction protocol v1

This optional provider-neutral protocol uses Pi's public event bus. It does not load another extension, import private code, or schedule work. The authoritative structural contract is [`src/prepared-compaction-protocol.ts`](../src/prepared-compaction-protocol.ts); compatible implementations may ship an identical copy without a runtime dependency.

## Discovery and ownership

An engine emits `pi.compaction-engine.v1:available` with its `CompactionEngineV1` object. A consumer can emit `pi.compaction-engine.v1:request` with `{accept(engine)}` to discover an already-loaded engine. Both directions support either extension load order. The engine reinstalls discovery on session start and removes its listener and source only after the last active session manager shuts down. Shutting down one manager does not disconnect another manager sharing the same extension factory. Consumers must detach their source, cancel their work, and remove listeners on shutdown, and rediscover on the next start.

`attachSource(source)` accepts one source and returns idempotent cleanup. A competing attachment throws rather than silently replacing another controller. No source means ordinary foreground compaction continues unchanged.

## Preparation and application

- `available(ctx)` reports whether this engine can accept a preparation now; it does not start work.
- `capture(ctx)` captures a compatible active prefix, request configuration, and bounded provider timeout. Its `isCurrent()` validates provider-relevant settings, session identity, model, ancestry, and working-set digests. Provider checkpoint mode also requires the captured thinking level, system prompt, and tool definitions to match. Text summary mode keeps its detached request-time prompt, tools, and thinking selection while allowing later changes to those three inputs; application measures current prompt/tool overhead against the current context budget. Captured ancestry and history remain immutable, and only Text summary accepts appended thinking-level metadata. Consumers should consult `isCurrent()` when thinking changes rather than imposing an unconditional cancellation policy. A fixed `reason` describes invalidation without values or credentials.
- Optional `diagnostics()` returns bounded UI-only `{ status, report, warning?, outcome?, reason? }` metadata. Optional terminal `outcome` is `failed`, `prepared`, `ready`, `recovered`, `discarded`, or `cancelled`; optional `reason` is a fixed safe category. A discarded or cancelled preparation is not a provider failure and must not itself pause future preparation. These fields are omitted until settlement; consumers should not treat a live progress snapshot as final. Producers retain a frozen final snapshot after settlement, automatically print their complete failure report in supported UI modes, and omit credentials, conversation content, raw headers, and checkpoint bodies. Consumers may poll while preparing and retain the final report for Status. Missing diagnostics preserves compatibility with older engines.
- `start(guard)` is one-shot and returns an implementation-owned `PreparedCheckpoint` handle. The consumer owns operation cancellation, run cancellation, timers, thresholds, status, and readiness. Pass the deadline separately as `deadlineSignal`: deadlines count as request failures, whereas owner cancellation does not. `ownsStatus` controls whether engine status may be written. Optional `failureReportOwner: "consumer"` promises that the consumer will display the final preparation failure together with its diagnostic snapshot, or explicitly report that the snapshot is unavailable. Supporting engines then suppress only their separate final preparation-failure notification; they still finalize and retain diagnostics. Foreground failures and successful EOF-retry reports remain producer-owned. Older consumers omit the flag and keep producer reporting. Older engines may ignore the flag and still print an earlier separate report; consumers must not omit their self-contained failure report to hide that compatibility duplication. The borrowed raw snapshot is released from the preparation handle immediately when starting; ready handles retain only the result, private binding, and digest guards.
- `PreparedCheckpoint.usable` reports preparation success. Optional `failure` is bounded, display-safe diagnostic text: producers must omit credentials, request/response bodies, conversation content, and stack traces. This engine emits fixed failure categories, observed HTTP status, or allowlisted network codes; unknown failures stay generic. Consumers should strip terminal controls and bound display length. Failed handles expose diagnostics only; they do not suppress a later foreground operation in the selected mode.
- `adopt(event, ctx, guard)` revalidates authorization, rebases retained suffixes exactly once, and checks token budget. It never starts inference. Outcomes are explicitly ready, stale, failed, or cancel.
- `draft(ctx, guard)` additionally previews Pi's finalized projection. Returning a draft is **not** a commit. The consumer confirms `checkpointId(ctx)` matches before reporting success or releasing a pending commit claim.
- `captureBoundary(ctx)` returns an exact boundary guard. Consumers must recheck it after notifications or any callback that can reenter the host, before returning a draft.

The core's sole `session_before_compact` handler calls `source.beforeCompact` while holding its foreground operation claim. `absent` means no prepared source result; `fallback` permits one fresh ordinary foreground operation in the selected mode, even after a failed preparation; its optional implementation-owned handle remains accepted for protocol compatibility; `cancel` forbids fallback; `ready` supplies a validated result. An automatic application must return `cancel`, not `absent` or `fallback`, when its exact candidate becomes invalid. An optional ready-result `isCurrent` is rechecked after core status cleanup so reentrant consumer changes cannot publish a stale result.

A fresh foreground operation uses current authentication, its own request timeout and cancellation signal, and the configured bounded provider retry policy. In Provider checkpoint mode, existing checkpoint-summary recovery and Pi-native fallback apply after failure; this does not loop or restart preparation. In Text summary mode, failure cancels compaction and preserves existing history without switching modes. A route paused after a compaction-specific OAuth rejection blocks Provider checkpoint dispatch, but does not block ordinary Text summary inference. Each logical operation may contain provider retries, so this is not a promise of one HTTP request. Context Management can replay one premature-EOF stream with a fresh collector after a short backoff; the original overall deadline includes both attempts and the delay. Before replay the engine revalidates provider/authentication binding and ownership. No partial checkpoint is reused, and explicit cancellation, terminal errors, authentication rejection, and protocol validation failures are not replayed.

Request deadline/run signals are not retained as ready-checkpoint validity: consumers may preserve a completed compatible result after stopping a run. Every adoption uses a fresh application signal and ownership guard. Optional structural timing sinks receive numeric phases only; scheduling and diagnostic presentation remain consumer-owned.

## Compatibility

The V1 names `PreparedCheckpoint` and `checkpointId` identify a prepared compaction result, not its storage format. `checkpointId(ctx)` returns the latest committed result ID for either Provider checkpoint or Text summary, and never an older superseded ID. Text summaries use separate versioned metadata and remain ordinary Pi plaintext compaction entries; consumers must not parse or manufacture either result format.

This protocol does not change serialized provider checkpoints. Existing v1–v4 checkpoints and ordinary tool-replay restoration remain engine-owned. Installing only this package does not proactively prepare checkpoints. Consumers are interchangeable participants; the engine does not identify or depend on any consumer package.

Text summary capture retains a minimal complete raw tail and summarizes only its preceding prefix. Adoption preserves that fixed tail plus every later message, validates tool pairs and the current prompt/tool-inclusive model budget, and verifies Pi's finalized projection. Its serialized draft boundary remains exact: even a thinking metadata append during that boundary requires a fresh boundary rather than publishing a stale draft. Provider checkpoint capture retains its existing checkpoint-aware replay projection.

Preparation requires the selected provider to match the active opaque checkpoint issuer. Cross-provider transfer remains an ordinary context/foreground operation, not speculative preparation. A cached plaintext transfer does not replace the persisted opaque checkpoint, so preparation stays unavailable on the other provider until foreground compaction replaces that checkpoint or the user switches back to its issuer. In-flight preparations retain exact model and non-token authentication guards even though persisted checkpoints can replay on another compatible model. Verified official ChatGPT OAuth ignores only matching request/provider access-token changes, under the [single-login assumption](../README.md); API keys, custom routes, and unverified provenance remain strict. Cancel preparation and restart before changing the ChatGPT login; a token-only account switch is indistinguishable from refresh.
