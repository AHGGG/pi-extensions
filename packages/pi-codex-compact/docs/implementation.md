# Codex Compact implementation reference

This document describes protocol, replay, and lifecycle details for extension and provider developers. For installation, safe recovery, and operational limits, use the [README](../README.md).

## Protocol and replay

A custom provider must honor Pi's public `transport: "sse"`, `onPayload`, and injected `fetch` options. Its backend must support the selected request fields and opaque replay; an API label or profile alone does not establish that support. The stored provider ID is diagnostic provenance, not a replay gate. Replay requires the real API label, resolved profile, exact model ID, and current authorization of any custom API profile.

1. Pi prepares compaction and selects the recent message suffix it will retain.
2. If an earlier compatible checkpoint is present, the extension identifies its boundary from the summary persisted on the active `CompactionEntry` and validates the retained suffix fingerprints.
3. Remote V2 projects that checkpoint into a normal Responses SSE request and appends exactly one final `compaction_trigger`.
4. Unary compact captures the provider-built payload and authentication, rewrites only the same-origin `/responses` path to `/responses/compact`, and requests JSON without making a normal inference call.
5. Context Management makes a streaming inference request, selecting the latest completed checkpoint and all safe completed output after it in event order.
6. Remote V2 and unary compact require one bounded non-empty opaque `compaction` item; unary output may precede it only with user-role retained messages.
7. It stores bounded replacement history with Pi suffix fingerprints, the real API label, and the resolved compatibility profile in versioned `CompactionEntry.details`. Context Management stores checkpoint-first history with an exact output suffix; the other protocols keep bounded user history with the checkpoint last.
8. On later compatible ordinary requests, it replaces an exactly validated marker with the intact persisted replacement history and one static work-replay boundary immediately before provider dispatch. Newer conversation items remain after that boundary.

Retained fingerprints follow Pi's finalized context projection, including pre-checkpoint omissions and replacements and suppression of nested older compaction summaries. For older checkpoints that fingerprinted raw entries, replay first verifies the complete saved raw snapshot, then derives its finalized retained suffix without changing session entries. Edits made after the checkpoint that change this covered suffix still fail validation rather than being silently absorbed. When an upgrade repairs a previously failed projection, the first correctly replayed request establishes a new prefix baseline; subsequent ordinary turns append to it.

The persisted entry remains the summary identity source, so replay does not depend on the wording generated by the currently installed extension version.
If persisted summary identity, fingerprints, model identity, payload shape, or marker count do not match exactly, the extension leaves Pi's visible fallback context unchanged instead of guessing.
Older v1 and v2 checkpoints are normalized to the current checkpoint format when read; their built-in API label determines the profile. They still replay only when the current route authorizes that API/profile/model combination.

### Ordinary-work replay boundary

`checkpoint-replay.ts` adds the deterministic developer message `PI_COMPACTION_WORK_RESUME_V1` after the restored history and before the newer conversation tail. It identifies completed maintenance handoffs and legacy OK acknowledgments as historical context, not a new request or evidence of task completion. It asks the model to follow the actual task and newer instructions, use tools only for unfinished authorized work, and respect completion, cancellation, and blockers.

This is a provider-prefix transition for correctness, not another continuation scheduler. It does not change the system prompt, tool definitions, saved checkpoints, or original history items. Within the new checkpoint prefix epoch the boundary remains at the same position with the same content; later ordinary requests append normally. A second invocation on an already rewritten payload has no marker and is skipped. All compatible owned protocols use the boundary because checkpoints can inherit older maintenance context.

The boundary is added only by the ordinary `before_provider_request` hook. Separate maintenance and recovery requests expand the persisted history through their existing path without the work-replay instruction. It cannot start a request, grant tool permission, infer task completion, or guarantee model compliance. See the [rebuild verification notes](rebuild-verification.md) for the current validation limits.

## Compaction ownership

Foreground compaction captures immutable serialized branch values before awaiting authentication. The live branch must retain that exact prefix, and appended entries must form direct descendants. Bookkeeping entries (`custom`, `usage`, `label`, and `session_info`) can extend the branch without canceling work. A `context_edit` append is accepted only when Pi's finalized session context remains identical; replacement and omission edits that change the input cancel it. New conversation messages, even hidden custom messages or subsequently omitted turns, new summaries, model/thinking changes, and different ancestry are not bookkeeping.

Ownership checks also require the effective system prompt and ordered active tool names, descriptions, and schemas to remain unchanged. State entries that indirectly change that request input cannot bypass cancellation. The same checks run after asynchronous authentication and provider work, before checkpoint publication, and before recovery or native fallback. Session replacement, reload, shutdown, explicit abort, model/settings changes, and completed tree navigation retain their existing invalidation paths. No extension-specific state identifier or cross-extension dependency is used.

## Experimental warm-ahead ownership and adoption

With `asyncEnabled: true`, a completed `turn_end` boundary may start one background request once context-window usage reaches `asyncThresholdPercent`. Eligibility requires completed, persisted conversation output and its tool results, not a partial stream or an unfinished tool exchange. The request captures an immutable preparation snapshot, its branch ancestry, model and route, settings, system prompt, and ordered active tool definitions. Preparation does not append a compaction entry, change checkpoint replay, or rewrite ordinary provider requests.

The foreground ownership rule above remains strict for foreground requests. Warm-ahead instead permits a validated descendant conversation tail after the immutable snapshot. Adoption must revalidate the snapshot and current projected context rather than blindly reuse Pi's later retained cut point. The adopted checkpoint covers the snapshot only; every post-snapshot conversation entry is retained in original order and content. Any incompatible ownership or projection change invalidates the candidate. Persistence starts a deliberate new model-visible prefix epoch; subsequent ordinary requests must preserve that new prefix. Exact tail preservation does not establish native suffix-cache reuse or any provider-reported cache hit.

Plain manual compaction, Pi automatic compaction, and opt-in native turn-boundary application can adopt a ready candidate. A ready result is validated before publication; an in-flight request may be awaited only until its original timeout expires. Adoption does not start a fresh timeout. A missing, stale, failed, or incompatible candidate returns to the existing foreground compaction policy, including checkpoint-aware recovery where applicable. Manual compaction with a pending request or custom instructions uses foreground preparation. Background work owns no recovery or native-compaction publication before adoption.

Settings/model changes, navigation, session replacement, reload, and shutdown release background work and discard unused results. User cancellation releases pending preparation but preserves ready results for manual adoption. Completion is not publication and cannot arm automatic continuation; only an actually adopted, persisted checkpoint is eligible under the existing continuation rules. Background requests can consume quota without adoption and provide no latency guarantee.


Ready warm-ahead checkpoints can return a native compaction draft at `turn_end` without calling the active-run-aborting `ctx.compact()`. Adoption revalidates the exact serialized boundary branch, snapshot, model, system prompt, tools, settings and authentication, and rejects incomplete tool pairs. The draft preserves other boundary entries and does not request continuation. Commit cleanup and completion logging happen only after the matching persisted checkpoint is observed at the next public lifecycle hook; a replaced draft is not reported as committed. Native boundary appends do not emit `session_compact`, and this extension does not synthesize that event.

Boundary application shares one captured per-entry digest across the boundary, adoption, and draft layers instead of retaining a full-history JSON string or nesting heavy validators. The exact raw-branch check is stricter than foreground adoption's bookkeeping-descendant guard; snapshot projection checks still run independently. Validation results are reused only within an unchanged synchronous phase, never across an `await`, and never from entry IDs, object identity, or revision alone. Request authentication, provider authentication, prepared-result adoption, draft generation, and final handoff each retain their fresh validation boundaries. Provider input remains detached from live messages and successful adoption makes no second model request.

With `logCompaction: true`, turn-boundary application records fixed numeric phases: `boundary`, `validation`, `preparedWait`, `authWait`, `rebind`, and `preview`, plus validation count and `extensionTotal`. Authentication timing includes lookup invocation and waiting, not the subsequent validators. These measurements cover extension work only: they exclude Pi's later native append, other extension handlers, disk persistence, and TUI rendering, and do not promise a latency ceiling. Successful timing is reported only after a matching persisted checkpoint is observed; rejected attempts can report immediately. No history, IDs, fingerprints, prompts, authentication values, or provider error bodies are included, and headless modes remain silent.

Escape cancels preparing requests. Ready checkpoints outlive their preparation run and remain manually reusable; a stopped candidate is not automatically applied on the next input. Pi does not recheck abort after all boundary handlers, so an already-returned validated draft can still commit if a later handler yields during a stop. No extra model turn is requested. Subsequent projection checks fail closed if another boundary participant changes covered history.

## Recovery and native fallback

Before the first checkpoint, remote failure leaves the `session_before_compact` result unset so Pi runs its default summary generator. With a valid compatible checkpoint and `checkpointRecovery: "summarize"`, recovery first validates the checkpoint projection and retained cut point, then makes ordinary inference with the checkpoint and tools disabled. Successful recovery publishes only validated plaintext output.

After a recovery request/provider failure, timeout, or invalid/oversized output, the hook leaves its result unset only while session, branch, model, settings, and ownership remain current. Pi owns native summarization, publication, and failure handling for manual, threshold, and overflow compaction. Recovery releases its timer, abort listener, controller, and stream before handoff. A changed dispatched backend blocks fallback. Invalid/incompatible checkpoints and projection/cut-point failures also cancel; explicit Cancel and stale or aborted work never fall through.

Native sees Pi's previous fallback summary marker and visible messages, not decrypted checkpoint history. Publication intentionally starts a new model-visible prefix epoch: the native summary supersedes the opaque checkpoint, and subsequent ordinary requests no longer expand it. The first post-publication request establishes the new baseline; later requests append normally. No new tools, system instructions, continuation, or protocol fallback are introduced. Notifications follow `notifyOnFallback` and UI availability and redact request secrets. See [Checkpoint recovery](../README.md#checkpoint-recovery) for context-loss, quota, and restoration risks.

## Context Management request and publication

Pi still decides when to compact. Only the extension-owned compaction request adds `context_management: [{"type":"compaction","compact_threshold":1024}]`, forces streaming with `store: false`, requests `reasoning.encrypted_content` while preserving other `include` fields and the provider's thinking effort, and appends a deterministic maintenance-only user message. Original instructions, history, and tool schemas remain provider-owned; `tool_choice: "none"` prevents new tool work. The request uses no `compaction_trigger`, server-side response ID, alternate credentials, or endpoint rewrite.

Successful completed-item events are authoritative: a stream can emit several checkpoints while omitting them from terminal response output. The extension persists the latest checkpoint and its exact completed assistant/reasoning suffix only after successful completion (`response.completed` or Codex's `response.done`). Post-checkpoint reasoning must have non-empty encrypted content for stateless replay; terminal output can supply missing encryption before publication, otherwise the request follows the documented fallback/recovery policy. It never executes generated tools or silently truncates that suffix. Missing checkpoints, malformed/unsafe output, exceeded bounds, permission errors, and unsupported capabilities follow the same fallback/recovery policy; very short history may not cross the 1,024-token server threshold. The normal inference can consume quota even if no checkpoint is returned, and fallback/recovery can make an additional summarization request. Safe generated output is retained as provider context, not displayed as new assistant work.

The maintenance instruction is request-local and asks for a work handoff rather than a fixed acknowledgment. Old opaque checkpoints and their exact output suffixes are not rewritten. The ordinary-work boundary explicitly separates that completed request from later work without dropping its output.

## Automatic continuation

Continuation state belongs to the session manager and original user run, not to the UI or each low-level agent retry. Only a matching persisted, extension-produced automatic Context Management checkpoint can arm the candidate. Manual, native, plaintext recovery, other-protocol, and restored checkpoint publication cannot arm it.

An ordinary provider request after publication consumes the candidate. Pi overflow retries, queued work, and pre-prompt or mid-turn requests therefore do not need a duplicate request. At `agent_before_settle`, a completed run with a compatible candidate can append one persisted, hidden `codex-compact:continue-v1` message at the context tail and return `continue: true`. Existing boundary drafts are preserved. An earlier continuation is reused only when the boundary context can actually continue; a flag alone after a completed assistant response is insufficient. Queued user work is checked through `ctx.hasPendingMessages()`, not the boundary's combined `pendingMessages` preview. That preview also contains deferred context-only custom messages, which permit continuation but do not schedule it. Context-only messages must not suppress the forced request. Custom messages queued to trigger work are handled by Pi's post-run queue drain and consume the candidate at normal provider dispatch. Later handlers can override the proposal through Pi's public boundary API.

The allowance is consumed before returning the proposal and resets only for a new original user run. Compaction during the forced continuation cannot start an extension-driven loop. Failure, abort, shutdown, replacement, reload, navigation, or model/settings incompatibility invalidates pending state. Asynchronous compaction results must still match the current owner and run before publication can arm them.

Ordinary requests preserve their prefix after each compaction, including the static work-replay boundary. The separate persisted continuation message is appended only when the bounded scheduler proposes another turn. Prior messages and the system prompt are not rewritten for continuation. Compaction changes the prefix intentionally; the first request after that change is the baseline for later ordinary requests. Scheduling work does not infer task completion or guarantee model compliance.

With `logCompaction: true`, lifecycle notices distinguish a committed continuation candidate, preparation of a normal work request, a proposed extra settlement turn, and suppression by existing work or lifecycle guards. These messages describe extension decisions, not proof that a provider accepted a request or that the model executed the task. They use the existing session-owned, UI-availability guards and contain no credentials, checkpoint bodies, or conversation contents. The logging preference persists through the existing settings file; print and JSON modes remain silent.

## OAuth rejection state

This fork retains upstream's maintenance handoff and single bounded continuation scheduler. The ordinary replay clarification is separate from scheduling; normal provider request preparation still consumes pending continuation before settlement can propose another request. The opaque replacement-history payload is unchanged; checkpoint v4 adds the snapshot cutoff and continues to read v1–v3 checkpoints.

Configured protocol and dispatched protocol have separate roles. Ownership and preference changes are checked using the configured route key; rejection dispatches use the authenticated protocol and endpoint. Successful checkpoint metadata, not the configured preference, determines whether Context Management continuation can be armed. This preserves continuation when Auto or V2 is adapted to Context Management.

For the official `openai`/`openai-responses` route, a fresh public `getProviderAuth` OAuth result must match the resolved request credential before protocol adaptation. Base URL and authorization-header overrides are excluded. Adapters without public provenance retain the original routing. The menu stores only the last resolved protocol keyed by the configured route; it never stores credentials or refreshes OAuth to render status.

Later compactions skip the rejected operation while compatible checkpoint replay remains enabled, even with fallback notifications off. Rejections are isolated by session manager and provider/model/API/profile/protocol plus the configured and dispatched endpoint origin/path (and Azure's `api-version`). Pi/provider authentication and request preparation still run to resolve the effective backend; rejected dispatches stop before network work. Changing the resolved compaction protocol (including selecting Context Management) or the backend permits a new attempt. Switching back remains paused.

Session start, `/reload`, resume, fork, replacement, and shutdown clear rejection state. The first 128 rejected identities are retained until reset; further identities follow ordinary failure handling without evicting earlier ones. The menu reports the last observed dispatch identity, which is rechecked at the next compaction. URL credentials and query secrets are excluded; non-Azure query routing changes, header-/body-only backend changes, and credentials on an otherwise unchanged route require `/reload` to retry. State is temporary, not a settings write or an entitlement cache.

## Codex CLI routing comparison

The examined Codex CLI source uses Remote V2 on its resolved Responses route: ChatGPT/Codex OAuth defaults to the Codex backend, while API keys default to the OpenAI API. This fork uses V2 for Codex-profile `auto` routes; OpenAI API-key and Azure `auto` routes use unary Compact API, while verified official OpenAI ChatGPT OAuth uses Context Management. Select Remote V2 explicitly to use that request form on a compatible API-key backend. Pi's newer OpenAI ChatGPT token-sharing OAuth is a different grant: neither an API label nor Codex CLI source establishes its compaction permission. The pre-dispatch adaptation is described above; it does not grant server permission or change authentication.

## Menu compatibility

Menu rendering inherits Kit's minimum one-cell width. Synthetic zero-column renders are clamped to one cell. This is a rendering compatibility limit, not an additional command mode.
